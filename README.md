# shaft-design-agent

A minimal agent that solves the minimum diameter of a mechanical shaft from
the raw statement of a problem (free text), applying four fatigue failure
criteria: DE-Goodman, DE-Gerber, DE-ASME Elliptic, and DE-Soderberg.

Built as a learning project based on [Building Agents from First
Principles](https://github.com/readytensor/building-agents), reusing the
loop + tool-calling mechanism from Episode 2, but with a different domain
design — see "Architecture decision" below.

## Scope of this v1

- Covers only shaft problems where the alternating and mean components of
  bending moment and torque (Ma, Ta, Mm, Tm) are already given in the
  statement — it does not derive them from a free-body diagram / bending
  moment diagram.
- Tested against Problem 7-1, Shigley's Mechanical Engineering Design,
  10th ed., Chapter 7 (Ma = 70 N·m, Ta = 45 N·m, Mm = 55 N·m, Tm = 35 N·m,
  Su = 700 MPa, Sy = 560 MPa, Se = 210 MPa, Kf = 2.2, Kfs = 1.8, n = 2.0)
  — see "Validation" below.
- Does not cover: multiple critical points along the shaft, deriving Kf/Kfs
  from geometry (keyways, fillets), or recomputing Se from Marin factors
  (Se must already be given, fully corrected).

## Architecture decision: why the formulas aren't in the LLM

The obvious temptation would be to let the model write and run a Python
calculation script (like `bash` in Episode 1). I chose not to do that, for
a few reasons found during development:

1. **Memorization disguised as reasoning.** Worked examples from
   well-known textbooks are widely replicated online — a model might
   "get" a result right because it memorized it, not because it actually
   computed it. A script generated by the model itself can contain
   effectively hardcoded values without that being obvious from reading
   just the final result.
2. **"Full-textbook-procedure" bias.** Models trained mostly on
   didactic material tend to apply the complete pedagogical procedure
   (every factor, every correction) even when the problem doesn't call
   for it — producing unnecessarily complicated or incorrect calculations
   by applying a step that shouldn't be there.
3. **Non-determinism.** Open-ended code generation can vary between runs,
   even for the same problem.

See [docs/comparison_raw_llm.md](docs/comparison_raw_llm.md) for a
measured example: the same problem solved by this agent (tool-verified)
vs. by a raw LLM with no tools, off by 6–7% with nothing in the output
hinting that anything was wrong.

The solution: the formulas (already solved for the diameter `d`) live as
fixed Python functions in `tools.py`, audited once by me. The LLM never
rewrites them — it only extracts parameters from the statement and decides
which tools to call. This division of responsibility is what makes the
result trustworthy and reproducible.

## What the LLM still does (and why this isn't over-engineering)

Extracting Ma, Ta, Mm, Tm and material properties from a free-text
statement — which can describe the same values in different ways — is a
language-interpretation task, not a calculation task. This is exactly
where an agent adds value over a plain deterministic script: a fixed
script would only work if the parameters already arrived organized and
labeled; the agent handles the raw statement, the way it's actually
written in the textbook.

The model also writes the discussion of the results (section 5 of the
answer, when the statement asks for it): why the criteria diverge, which
one is most/least conservative, when two results are numerically close
enough to be practically equivalent, and a practical takeaway for which
to use. This draws on the model's knowledge of fatigue theory to interpret
numbers that are already known to be correct (they came from the tools),
not to produce them — the same reasoning-vs-arithmetic split as
everywhere else in this project. It's a genuinely useful capability (see
`docs/example_run.md` for an example), but unlike the diameters
themselves, this prose isn't independently verified. During development,
runs of this agent occasionally reordered criteria inconsistently, or
stated an approximate percentage difference that turned out to be
imprecise once checked against the actual numbers — which is why
`system_prompt.md` explicitly forbids the model from doing any arithmetic
in its own prose (see rule 6 there), not just in calculating the diameter
itself. Read the discussion the way you'd read a colleague's reasoning:
probably right, worth a second look before relying on it.

## Why sections 1-4 of the answer aren't written by the LLM either

The same principle above ended up applying to formatting, not just math.
Early versions asked the model to write out the extracted parameters,
criteria applied, and tool results in prose — it repeatedly skipped
straight to the discussion, treating "I already called the tool" as
equivalent to "I already told the user," even with explicit instructions
not to.

Sections 1-4 of the final answer are now generated directly from the
executed tool calls, in `agent.py` (`_render_deterministic_sections`) —
no LLM involved, since they're pure restatement of tool inputs/outputs
with no reasoning required. The model is only responsible for sections
5-6 (discussion and assumptions), which genuinely need its reasoning. See
`system_prompt.md` for the exact split.

## Validation

The four tools were checked against the official solutions manual for
Problem 7-1 above and matched exactly:

| Criterion        | Agent output | Solutions manual |
|-------------------|:-----------:|:-----------------:|
| DE-Goodman        | 27.27 mm    | matches |
| DE-Gerber          | 25.853 mm   | matches |
| DE-ASME Elliptic   | 25.769 mm   | matches |
| DE-Soderberg       | 27.696 mm   | matches |

The results also follow the theoretically expected order of conservatism:
Soderberg > Goodman > Gerber ≈ ASME Elliptic. When adapting this to another
problem, solve it by hand (or check a solutions manual) first and compare
against the tools' output before trusting it — this project deliberately
avoids trusting the LLM's own arithmetic, and that same caution should
apply to any new formula added later.

This validation is enforced by an automated test (`tests/test_tools.py`),
not just claimed in prose:

```bash
pytest tests/test_tools.py -v
```

See [docs/example_run.md](docs/example_run.md) for a full, real run:
problem statement in, tool calls made, complete response out.

## Usage

```bash
python -m venv venv
source venv/bin/activate       # Windows: venv\Scripts\activate
pip install -r requirements.txt
cp .env.example .env           # fill in the key for your chosen provider
```

`TASK` in `agent.py` comes pre-filled with Problem 7-1 — the same one
validated in `docs/example_run.md`. Run it as-is to reproduce that:

```bash
python agent.py
```

To solve a different problem, edit `TASK` with your own raw problem
statement first, then run the same command.

## Known limitations / next steps

This v1 solves the diameter given Ma, Ta, Mm, Tm and material properties
already known — it doesn't derive them from the physical layout of the
shaft. A more complete project would work backward from the actual
machine elements driving the design:

- Motor torque, computed from power and rotational speed.
- External loads from the elements mounted on the shaft — pulleys,
  gears, chains/sprockets — translated into forces and moments at their
  mounting positions.
- Support reactions at the bearings, solved from static equilibrium
  given those loads and positions.
- Bending-moment and torque diagrams along the shaft's length, to locate
  the critical section(s).
- Combined bending-and-torsion stress analysis at each critical point,
  feeding into the fatigue criteria this v1 already calculates.

Each of these is a distinct calculation stage with its own well-defined
equations — the same principle behind this project's architecture
(deterministic tools, not LLM arithmetic) would apply to each one: a
human-audited function per stage, with the LLM only responsible for
extracting the physical layout (motor specs, element types and
positions) from the problem description and orchestrating which stage
to call.
